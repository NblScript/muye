## 1. 演示优先

**信念**：这是一个竞赛演示系统，稳定性压倒一切。

**推论**：
- 新功能必须通过 `./scripts/demo.sh` 验证
- 不引入未经充分测试的复杂依赖
- 降级策略优于完美方案
- 单机可运行是硬性约束

## 2. 领域驱动，事件解耦

**信念**：按业务边界组织代码，域间通过事件通信。

**推论**：
- `modules/` 下按 detection/decision/drone/infra 分包
- 域间禁止直接函数调用，必须通过 `EventBus`
- 新增跨域功能 → 先定义事件类型，再实现生产者/消费者

## 3. 结构化输出，不信任 LLM

**信念**：LLM 输出必须经过机器校验，不能依赖纯 prompt 约束。

**推论**：
- Qwen API 返回必须通过 jsonschema 校验
- 定义明确的输出 schema（`models/schemas.py`）
- 校验失败时重试或降级，不使用未校验的输出

## 4. SQLite 是够好的数据库

**信念**：对于竞赛演示场景，SQLite 的简单性远超 PostgreSQL 的功能。

**推论**：
- 零运维，单文件可移植
- WAL 模式支持并发读
- 不引入 ORM 迁移工具（直接 SQL DDL）
- 备份 = 复制文件

## 5. 事件流可追溯

**信念**：所有系统行为必须可通过事件流重放。

**推论**：
- `data/logs/demo_events.jsonl` 是系统的"黑匣子"
- 每个关键操作必须发出事件
- 事件格式：`{timestamp, event_type, source, payload}`

## 6. 代码即文档

**信念**：好的代码结构比注释更有价值。

**推论**：
- 函数名和变量名必须自解释
- 仅在 WHY 非显而易见时添加注释
- 不写"WHAT"注释（代码本身说明了什么）
- 公共 API 必须有简短 docstring

## 7. 边界处防御，内部信任

**信念**：在系统边界严格校验，内部代码信任调用者。

**推论**：
- API 入口：Pydantic 模型校验
- LLM 输出：jsonschema 校验
- 文件上传：类型+大小限制
- 内部函数：不重复校验参数

## 8. 渐进式披露

**信念**：信息应该分层组织，而不是塞进一个大文件。

**推论**：
- `AGENTS.md` 是入口地图，不是完整文档
- 每个关注点有独立的文档文件
- 文档间通过链接互联，不重复内容
